# Ejercicio 04 — Migraciones con Alembic

⏱️ 1 h 30 min · Teoría previa: [04](../../1-teoria/04-alembic-migraciones-del-esquema.md)

## Objetivo

Cambiar las tablas de una base que **ya tiene datos**, paso a paso y sin perderlos, con **Alembic**:

- preparar Alembic en un proyecto: `alembic init`, `alembic.ini` y `env.py`;
- generar una migración a partir de los modelos con `--autogenerate`, **leerla** y aplicarla;
- ver dónde apunta Alembic la revisión, y la historia de migraciones;
- añadir una columna que admite `NULL` y otra que no, y ver por qué la segunda falla;
- renombrar una columna sin perder sus datos, cuando `--autogenerate` se equivoca;
- deshacer con `downgrade`, comprobar con `alembic check` y ver el SQL con `--sql`.

Es lo que harás en tu proyecto, con `loads` y `readings`. Aquí la tabla es `stations`, en una base aparte, `migraciones`. Ejercicio **guiado**: esta vez trabajas sobre todo en la terminal; en `models.py` descomentas cada paso cuando el README lo dice, y `main.py` solo enseña cómo está la base. No se entrega.

## Antes de empezar

El mismo PostgreSQL de los ejercicios anteriores, con una base **nueva**, vacía, para que Alembic no vea las tablas de los otros ejercicios:

```bash
cd bootcamp/week-19-postgresql_psycopg_sqlalchemy_y_alembic/2-practicas/ejercicio-04-migraciones-con-alembic/starter
docker compose up -d --wait
docker compose exec db createdb -U practicas migraciones
uv run python main.py
```

```
revisión: None
todavía no existe la tabla stations
```

`createdb` es un programa que trae PostgreSQL: crea la base `migraciones` dentro del mismo servidor. `main.py` enseña tres cosas cada vez que lo ejecutes: en qué **revisión** está la base (todavía ninguna), las columnas de `stations` y sus filas.

## Pasos

### 1. Preparar Alembic

```bash
uv run alembic init migrations
ls migrations
```

```
...
Please edit configuration/connection/logging settings in /.../starter/alembic.ini before proceeding.
README  env.py  script.py.mako  versions
```

`alembic init` crea `alembic.ini` (la configuración) y la carpeta `migrations/`: `env.py`, que Alembic ejecuta en cada orden; `script.py.mako`, la plantilla de cada migración; y `versions/`, donde irán las migraciones.

Ahora dile a `env.py` **con qué modelos** comparar y **a qué base** conectar. Abre `migrations/env.py` y haz dos cambios:

1. Debajo de `from alembic import context`, añade:

   ```python
   from models import URL, Base
   ```

2. Cambia la línea `target_metadata = None` por estas dos:

   ```python
   target_metadata = Base.metadata
   config.set_main_option("sqlalchemy.url", URL)
   ```

`models` se puede importar porque `alembic.ini` trae `prepend_sys_path = .`: la carpeta desde la que ejecutas entra en el camino de búsqueda de Python. Y la URL sale de `models.py`, no de `alembic.ini`, que lleva una de mentira (`driver://user:pass@localhost/dbname`). En tu proyecto saldrá de `OBSERVATORIO_DATABASE_URL`, porque `alembic.ini` va a Git y la URL lleva una contraseña.

### 2. La primera migración

En `models.py`, descomenta el **PASO 2**: la clase `Station`, con `id` y `name`. Después:

```bash
uv run alembic revision --autogenerate -m "create stations"
```

```
...
INFO  [alembic.autogenerate.compare.tables] Detected added table 'stations'
Generating .../starter/migrations/versions/9397e8d640fc_create_stations.py ...  done
```

Alembic se conectó a `migraciones`, la comparó con `Base.metadata` y escribió en un archivo lo que falta. El número (`9397e8d640fc`) es el **identificador de la revisión**: el tuyo será otro. Abre el archivo y **léelo** antes de aplicar nada:

```python
def upgrade() -> None:
    """Upgrade schema."""
    # ### commands auto generated by Alembic - please adjust! ###
    op.create_table('stations',
    sa.Column('id', sa.Integer(), nullable=False),
    sa.Column('name', sa.String(length=50), nullable=False),
    sa.PrimaryKeyConstraint('id', name=op.f('pk_stations')),
    sa.UniqueConstraint('name', name=op.f('uq_stations_name'))
    )
    # ### end Alembic commands ###


def downgrade() -> None:
    """Downgrade schema."""
    # ### commands auto generated by Alembic - please adjust! ###
    op.drop_table('stations')
    # ### end Alembic commands ###
```

Cada migración sabe **ir** (`upgrade`) y **volver** (`downgrade`). Los nombres `pk_stations` y `uq_stations_name` salen de la `naming_convention` de `Base` en `models.py`; sin ella, PostgreSQL inventaría unos, y una migración futura no sabría cómo se llaman. El aviso `please adjust!` va en serio: es un borrador.

Aplícala y mira la base:

```bash
uv run alembic upgrade head
uv run python main.py
```

```
...
INFO  [alembic.runtime.migration] Running upgrade  -> 9397e8d640fc, create stations
revisión: 9397e8d640fc
columnas: id INTEGER, name VARCHAR(50)
fila: {'id': 1, 'name': 'Norte'}
fila: {'id': 2, 'name': 'Sur'}
```

`head` es la última migración. Las dos filas las añade `main.py` la primera vez que encuentra la tabla vacía: a partir de aquí, cada migración trabaja sobre **datos de verdad**.

### 3. Dónde apunta Alembic

```bash
uv run alembic current
uv run alembic history
docker compose exec db psql -U practicas -d migraciones -c 'SELECT * FROM alembic_version'
```

```
9397e8d640fc (head)
<base> -> 9397e8d640fc (head), create stations
 version_num
--------------
 9397e8d640fc
(1 row)
```

Alembic guarda la revisión actual en una tabla de la propia base, `alembic_version`. Así sabe qué migraciones faltan: en tu máquina, en la de un compañero o en un servidor, cada base tiene la suya.

### 4. Una columna que admite `NULL`

En `models.py`, descomenta el **PASO 4** (`altitude: Mapped[int | None]`). Después:

```bash
uv run alembic revision --autogenerate -m "add altitude"
uv run alembic upgrade head
uv run python main.py
```

```
...
INFO  [alembic.autogenerate.compare.tables] Detected added column 'stations.altitude'
...
INFO  [alembic.runtime.migration] Running upgrade 9397e8d640fc -> 371a9a36ca56, add altitude
revisión: 371a9a36ca56
columnas: id INTEGER, name VARCHAR(50), altitude INTEGER
fila: {'id': 1, 'name': 'Norte', 'altitude': None}
fila: {'id': 2, 'name': 'Sur', 'altitude': None}
```

La migración es una línea, `op.add_column(...)`, con `nullable=True`. Las filas que ya había se quedan con `NULL` en la columna nueva: no hay problema, porque la admite.

Pon una altitud a Norte, para tener un dato que proteger en el paso 6:

```bash
docker compose exec db psql -U practicas -d migraciones -c "UPDATE stations SET altitude = 2600 WHERE name = 'Norte'"
```

```
UPDATE 1
```

### 5. Una columna que no admite `NULL`

En `models.py`, descomenta el **PASO 5** (`region: Mapped[str]`, sin `| None`). Después:

```bash
uv run alembic revision --autogenerate -m "add region"
uv run alembic upgrade head
```

```
...
sqlalchemy.exc.IntegrityError: (psycopg.errors.NotNullViolation) column "region" of relation "stations" contains null values
[SQL: ALTER TABLE stations ADD COLUMN region VARCHAR(50) NOT NULL]
```

La columna nueva es `NOT NULL`, pero Norte y Sur ya existen y no tienen región: PostgreSQL no puede añadirla. En una base vacía (la de tus tests, por ejemplo) habría funcionado, y el fallo habría salido en la de verdad. La migración no se aplicó a medias: en PostgreSQL, el `ALTER TABLE` está dentro de una transacción, y `alembic current` sigue en `371a9a36ca56`.

Arréglalo con un valor **por defecto en el servidor**, en los dos sitios:

1. En `models.py`, cambia la línea de `region` por:

   ```python
       region: Mapped[str] = mapped_column(String(50), server_default="sin región")
   ```

2. En la migración `..._add_region.py`, añade `server_default='sin región'` a la columna:

   ```python
       op.add_column('stations', sa.Column('region', sa.String(length=50), nullable=False, server_default='sin región'))
   ```

```bash
uv run alembic upgrade head
uv run python main.py
uv run alembic check
```

```
...
revisión: aa55fd1d10ca
columnas: id INTEGER, name VARCHAR(50), altitude INTEGER, region VARCHAR(50)
fila: {'id': 1, 'name': 'Norte', 'altitude': 2600, 'region': 'sin región'}
fila: {'id': 2, 'name': 'Sur', 'altitude': None, 'region': 'sin región'}
...
No new upgrade operations detected.
```

PostgreSQL rellena las filas que ya existían con el valor por defecto. `alembic check` compara los modelos con la base, como `--autogenerate`, pero sin escribir nada: si dice `No new upgrade operations detected`, modelos y migraciones están de acuerdo. El test `test_the_migrations_match_the_models` de tu proyecto hace lo mismo.

### 6. Renombrar sin perder datos

En `models.py`, cambia el **nombre** de la columna del PASO 4: de `altitude` a `elevation`.

```python
    elevation: Mapped[int | None]
```

```bash
uv run alembic revision --autogenerate -m "rename altitude to elevation"
```

```
...
INFO  [alembic.autogenerate.compare.tables] Detected added column 'stations.elevation'
INFO  [alembic.autogenerate.compare.tables] Detected removed column 'stations.altitude'
```

**No apliques todavía.** Abre la migración nueva:

```python
    op.add_column('stations', sa.Column('elevation', sa.Integer(), nullable=True))
    op.drop_column('stations', 'altitude')
```

Alembic solo ve dos fotos, antes y después: falta una columna y sobra otra. No puede saber que es la misma. Esta migración **borraría** la columna `altitude`, con el 2600 de Norte dentro. Cámbiala, en `upgrade` y en `downgrade`, por un renombrado:

```python
def upgrade() -> None:
    """Upgrade schema."""
    op.alter_column('stations', 'altitude', new_column_name='elevation')


def downgrade() -> None:
    """Downgrade schema."""
    op.alter_column('stations', 'elevation', new_column_name='altitude')
```

```bash
uv run alembic upgrade head
uv run python main.py
uv run alembic check
```

```
...
revisión: d58289dbc4c2
columnas: id INTEGER, name VARCHAR(50), elevation INTEGER, region VARCHAR(50)
fila: {'id': 1, 'name': 'Norte', 'elevation': 2600, 'region': 'sin región'}
fila: {'id': 2, 'name': 'Sur', 'elevation': None, 'region': 'sin región'}
...
No new upgrade operations detected.
```

El 2600 sigue ahí. Por eso cada migración se **lee** antes de aplicarla, y por eso las migraciones van a Git y se revisan en el *pull request*, como el código.

### 7. Volver atrás, y ver el SQL

```bash
uv run alembic downgrade -1
uv run python main.py
uv run alembic upgrade head
uv run alembic history
```

```
INFO  [alembic.runtime.migration] Running downgrade d58289dbc4c2 -> aa55fd1d10ca, rename altitude to elevation
revisión: aa55fd1d10ca
columnas: id INTEGER, name VARCHAR(50), altitude INTEGER, region VARCHAR(50)
...
aa55fd1d10ca -> d58289dbc4c2 (head), rename altitude to elevation
371a9a36ca56 -> aa55fd1d10ca, add region
9397e8d640fc -> 371a9a36ca56, add altitude
<base> -> 9397e8d640fc, create stations
```

`downgrade -1` deshace la última migración con su `downgrade()`: la columna vuelve a llamarse `altitude`, con su dato. `upgrade head` la rehace. Las migraciones forman una **cadena**: cada una apunta a la anterior (`down_revision`).

Y si en lugar de ejecutar quieres **ver** el SQL, para revisarlo o para dárselo a quien administra la base:

```bash
uv run alembic upgrade head --sql 2>/dev/null | grep -E "^(CREATE|ALTER)"
```

```
CREATE TABLE alembic_version (
CREATE TABLE stations (
ALTER TABLE stations ADD COLUMN altitude INTEGER;
ALTER TABLE stations ADD COLUMN region VARCHAR(50) DEFAULT 'sin región' NOT NULL;
ALTER TABLE stations RENAME altitude TO elevation;
```

Con `--sql`, Alembic no se conecta: escribe el SQL de toda la cadena, desde cero, y no toca la base.

Por último, `downgrade base` deshace **todas** las migraciones. Pruébalo y mira lo que queda:

```bash
uv run alembic downgrade base
uv run python main.py
```

```
...
revisión: None
todavía no existe la tabla stations
```

El último `downgrade` es un `DROP TABLE`: los datos se fueron con la tabla. En tu máquina no pasa nada; en una base con datos de verdad, un `downgrade` se piensa igual que un `upgrade`. Para terminar, deja la base en `head` (`uv run alembic upgrade head`) o bórrala entera:

```bash
docker compose exec db dropdb -U practicas migraciones
docker compose down
```

## 🧯 Si algo sale mal

| Síntoma | Qué hacer |
|---|---|
| `Can't load plugin: sqlalchemy.dialects:driver` | `env.py` no pone la URL: falta `config.set_main_option("sqlalchemy.url", URL)` |
| `ModuleNotFoundError: No module named 'models'` | Ejecutas `alembic` desde otra carpeta: hazlo en `starter/`, donde están `models.py` y `alembic.ini` |
| `FAILED: No config file 'alembic.ini' found` | Lo mismo: ejecuta desde `starter/`, o no hiciste el paso 1 |
| `database "migraciones" does not exist` | Te saltaste el `createdb` de "Antes de empezar" |
| La migración sale vacía (`pass`) | No descomentaste el paso en `models.py`, o no guardaste el archivo |
| `Detected removed table 'readings'` (o `'notes'`) | Estás contra la base `practicas`, la de los otros ejercicios: la URL de `models.py` debe terminar en `/migraciones` |
| `Can't locate revision identified by '...'` | Borraste un archivo de `versions/` que ya estaba aplicado: `dropdb` y `createdb`, y vuelve a empezar |
| `Target database is not up to date.` | Hay una migración sin aplicar: `uv run alembic upgrade head` antes del siguiente `revision --autogenerate` |
